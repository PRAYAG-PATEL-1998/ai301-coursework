# Rubric: is this pull request ready to submit?

The four failure families are the harness's categories: silent drift,
not tested, unreviewable, standards wall. Every check below belongs to
one of them; a package that fails none is a clear accept. The honest
outcome rule holds throughout: a PR that discloses a shortfall, or a
plan that records a deviation, is judged as the disclosed work it is.
Only silence fails. "Less than everything" is never a reason to hold on
its own.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | Silent drift. The list of files in the Candidate PR's diff (every `---`/`+++` header, or `git diff main...HEAD --stat` live), read against the plan's Files line, its scope (in and not-in lines), and any Deviations note. | Pass if every changed file, and every code hunk in it, is something the plan names (the file, or its folder or area; "a changelog entry" counts as naming the changelog file; tests for the fix count when the plan promises tests) or something a recorded deviation note explains, AND nothing the plan lists under "not in scope" is touched, AND everything the plan promised is present or its absence is disclosed in the description. Fail if the diff holds a file or hunk the plan never asked for with no note (a helper, rename, refactor, new option, or "while I'm here" edit), or touches a not-in area, or silently drops a planned part. Count each file by its own header: a file that appears in the diff is changed, whatever the description says. | required |
| description-true-to-diff | Silent drift. Each factual sentence in the Candidate PR's description (what changed, what was added or not added, "implements the plan exactly", "no other changes", "tests added", "changelog entry added", the Changes bullets), read against the diff's files and hunks and the commit list. | Pass if every claim is true of the diff: each thing said to be added, changed, or left out is (or is not) in the diff exactly as stated, and any claim of fidelity to the plan ("exactly", "no changes beyond it") is borne out by diff-within-plan. Fail if any claim is contradicted or unsupported by the diff: a claimed test or changelog file that is not in the diff, "no changes beyond the plan" while the diff holds an unplanned file, a described change the diff does not make. A description that discloses a deviation or a shortfall passes this check for the disclosed item. | required |
| fix-shown-before-after | Not tested. The Candidate PR's test-evidence section, read against the plan's test plan and the repro evidence's own steps. | Pass if the evidence re-runs the plan's own reproduction (the command or action the plan's test plan names) and names a specific observed result both before and after the change: an error message, exit code, number, row count, or the visible output, either pasted or given as the result beside the command (a `# before: ...` / `# after: ...` annotation that quotes the concrete result counts), with the expected-after outcome stated or visible (for example 41 rows then 42, an error then a clean parse, `code = 1` then `code = 0`). Fail if the after-state is only asserted to be right without a specific observed result ("matches the expected output", "behaves as expected", "works", "tests pass", "verified manually"), if there is no after-run or no observable named for the before, if the after-run is a different test than the one that showed the failure, or if the plan's test plan names an additional check on the fix and the evidence says nothing about its outcome and does not disclose that it was not run. An additional test-plan item passes when the evidence reports its concrete outcome, even in a sentence (for example "same-key redefine prints the one-time warning"). A disclosed "not run, because ..." for such an item passes. | required |
| repo-checks-outcome | Not tested. The test-evidence section's output for the repo's own checks (the suite, linter, type checker, build, or whatever the plan's test plan and the repo-facts block's contribution asks name), read against those named checks. | Pass if each of the repo's own checks that the plan or the repo-facts block name has a concrete outcome in the evidence: a pass count ("312 passed"), "clean", "ok", an exit status, whether pasted or stated in a sentence, or a check that failed or could not run is reported honestly with its reason. Fail if a named check is absent with no word about it, or is claimed only vaguely with no outcome that could be wrong ("tests pass", "all checks pass", "verified", with no count, no named check, no output), or if the evidence contradicts the claim (failures or errors in the output under a "passes" claim). A check that failed with the reason disclosed passes; a hidden failure fails. | required |
| diff-reviewable | Unreviewable. The hunks of the Candidate PR's diff, line by line, plus the commit list. | Pass if the diff reads as the fix and its tests and nothing else: every added or removed line contributes to the planned change. Fail if the diff holds debris that buries the change: debug prints or logging left in, commented-out code, dead code or unused definitions, formatting or whitespace churn, a rewrite or reordering of lines the fix did not need (equal behavior, different shape), a file of unrelated edits, or generated or scratch files committed. Judge each hunk by whether the plan's change needs it, not by how short the diff is. | required |
| template-asks-honored | Standards wall. The repo-facts block's `pull requests:` line (template sections and checklist asks) and any `contribution policy` ask for a PR, read against the Candidate PR's description and diff. | Pass if every ask the repo states for a PR is met with real content, not boilerplate: each template section present and filled in the author's own words about this change; the issue referenced the way the repo asks (for example a `Closes #N` line); each ask that is an action done in the diff or explicitly accounted for (a changelog entry, tests added, docs updated, a seeded-bug marker removed, a conventional-commit title) and each ticked checkbox true of the package. Fail if a stated ask is visibly ignored: a required section missing or left as a placeholder or a template comment, the issue not referenced where asked, an asked-for changelog or test not in the diff and not explained, or a box ticked that the evidence contradicts. Pass trivially on any ask the repo does not state: where no template or ask exists, nothing is graded here. | required |
| ai-policy-honored | Standards wall. The repo-facts block's `contribution policy` line (including any AI-use rule), read against the Candidate PR's description. | Pass if the stated policy asks nothing about AI use, or its disclosure ask applies only to issues and comments and not to pull requests; or if the policy does require AI disclosure, human-written text, or understanding of the work in PRs and the description says so in the author's own words, naming the tool and the extent of assistance where the policy asks for them. Fail if the policy requires disclosure (tool and extent) or states another AI rule that applies to this PR and the description omits it or answers it with an empty gesture. | required |
| maintainer-direction-engaged | Standards wall. The Thread highlights and Issue body for explicit maintainer direction (lines marked COLLABORATOR, MEMBER, or OWNER, or the repo-facts policy restated in the thread): a constraint, a "discuss first" gate, a named restriction, a chosen option, or work already in flight. Read against the Candidate PR's description and diff. | Pass if the thread holds no explicit direction, or the PR follows it, or the description names the direction and gives a reason it departs. Fail if the thread holds explicit maintainer direction (for example a contribution gate, a ban on an approach, or a chosen option) and the PR neither follows it nor mentions it. | required |
| title-says-what-and-where | The Candidate PR's title, read against the diff. | Pass if the title names what changed and where, so a maintainer could tell what the PR does without opening it. Fail if it is generic ("fix bugs", "updates"). Reported in the summary only. | preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. Any `required`
check graded `fail` or `unclear` results in `reject`: a PR that cannot
be verified from its package is not ready to submit. The `preferred`
check never changes the verdict; report it in the summary. A PR that
does less than the whole issue and says so is not a reason to reject, and
a polished, confident description is never a reason to accept: the
verdict follows the checks. A failed `diff-within-plan` or
`description-true-to-diff` decides `reject` however clean the code reads,
because silent drift fails however good the code is.
