# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's Diagnosis (its stated cause), read against every numbered step AND every control run in the Repro evidence block. Where the Diagnosis says it takes its cause "from the thread", the thread is only a claim to test, never proof. | Pass if the stated cause is consistent with every step and control in the repro evidence and accounts for what differs between the failing run and the control runs. The repro need not prove the code-level mechanism: a cause that fits the evidence and is stated as the plan's reading of it passes, even when some internals are inference. Fail if any step or control rules the cause out (for example, the failure still happens with the suspected component removed, disabled, or bypassed, or the timing or output shows the cost without the suspected component in the loop), or if the cause is simply copied from the thread (or from a thread comment) and nothing in the repro evidence points at it. Unclear only if the repro evidence has no control or step that bears on the cause either way. | required |
| bounded-scope | The plan's Scope statement (in and not-in lines) and its list of changes or approach steps, read against the one failing behavior the repro evidence shows. | Pass if every listed change is needed to make that one failing behavior stop, and the plan states what it leaves out. A plan that does less than the whole issue passes if it says what it defers and why. Fail if any change goes beyond the failing behavior: a refactor, rename, migration, new option or setting, redesign, rewrite, port, or extra feature the repro does not require, even when the core fix is also in the plan. | required |
| buildable-by-stranger | The plan's Changes/Approach and Files sections. | Pass if a stranger could start work from the plan alone: it names a specific file, module, or code path where the change goes (naming the exact function may wait for tracing) and a chosen approach for each change. Fail if the location or the approach itself is left undecided ("somewhere", "whichever is easier", "investigate", "maybe also", "not sure which layer"), or if no file, module, or code path is named. A plan that picks its approach and location but says it will pin the exact function while tracing still passes. | required |
| test-decisive | The plan's Test plan, read against the Repro evidence's steps and observed outputs. | Pass if the test plan names an observable before/after outcome tied to the repro's own steps (a command or action plus the specific result expected after the fix, such as a number, exit code, or output) that would visibly differ if the fix did not work. Fail if the outcome is vague ("should feel fast", "nothing else breaks") or the only test is a generic one ("run the full test suite") that names no outcome for this fix. | required |
| thread-engaged | The plan comment, read against the Thread highlights (and the Issue body) for explicit maintainer direction: a stated constraint, a named culprit or location, a chosen option, a requested action, or work already in flight (open PRs, prior art). | Pass if the thread holds no explicit direction, or the comment follows it, or the comment names the direction and gives a reason it departs from it. Fail if the thread holds explicit maintainer direction and the comment (and plan) neither follow it nor mention it. Also fail if the comment promises something the plan does not contain (a timeline, extra work, an assignment request standing in for a plan). | required |
| conventions-met | The plan comment, read against the Repo facts block: the contribution policy line (including any AI-use rule) and the bug-report template asks. | Pass if the comment does what the stated policy requires of a comment on an issue. Where the policy requires disclosing AI assistance (tool and extent) in issues or comments, or requires human-written comments, the comment must say so in its own words. Where the policy states no AI rule, or its disclosure ask applies only to pull requests, nothing is required. Fail if the policy requires something of this comment and the comment omits it. | required |
| honest-unknowns | The plan's Risks or Unknowns text and any hedged claims in the plan comment. | Pass if open questions the plan cannot yet answer are stated as questions, not as settled facts. Fail if the plan states an unverified guess as certain. | preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. Any required check graded `fail` or `unclear` results in `reject`: a plan that cannot be verified from the package is not ready to build from. The `preferred` check never changes the verdict; report it in the summary. A smaller-than-the-issue plan that states what it defers is not a reason to reject. Polished prose is never a reason to accept: the verdict follows the checks, in particular a failed diagnosis-grounded decides `reject` however well the rest reads.
